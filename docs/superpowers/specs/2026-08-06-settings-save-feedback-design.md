# 设置保存分阶段反馈与后台应用设计

## 背景

桌面 Web 的设置页当前在提交 `PUT /api/config` 后，会一直等待运行时热重载完成。配置文件通常能在毫秒级写入，但热重载需要安全排空对话、事件处理和后台 LLM 工作；一次真实日志中，`config.toml` 与 12 个运行时组件在 `10:55:33` 已完成写入和重建，而响应直到 `10:56:10` 才结束，期间完成了一次 `soul.speculate` LLM 调用。

前端虽然把按钮改成“保存中…”，保存栏左侧仍显示“已修改 1 项，未保存”，并把主要进度放在不醒目的只读文本框中。用户既无法区分“文件已保存”和“运行时已应用”，也容易把等待热重载理解成页面卡死。

## 目标

1. 配置通过校验并成功写入 `config.toml` 后，HTTP 请求立即返回，不等待热重载结束。
2. 前端收到写盘成功响应后立即结束“保存中”状态，并明确显示“配置已保存，正在后台应用…”。
3. 后台热重载继续沿用现有安全排空、latest-wins 合并、失败回滚和运行时事件机制。
4. 热重载成功或失败后，前端展示最终状态并与后端配置重新同步。
5. 连续编辑和连续保存时，旧修订事件不得覆盖更新的本地修改或更新的应用状态。

## 非目标

- 不优化具体 LLM、内容发现或推荐任务本身的耗时。
- 不修改配置字段、校验规则、认证方式或配置文件格式。
- 不修改浏览器扩展设置页的交互；本次范围仅为桌面 Web `/web` 与共享后端 `PUT /api/config` 合约。共享合约变为 202 后必须验证扩展现有调用仍把所有 2xx 响应视为成功。
- 不处理小红书候选生成问题，该问题单独诊断并在另一个 PR 中修复。

## 方案选择

采用“写盘后统一进入后台应用队列”的方案。后端不再区分“通道繁忙时排队”和“看似空闲时同步热重载”；每一次有效配置写入都生成修订号、进入现有配置应用队列并立即返回 HTTP 202。

不采用仅增加前端动画的方案，因为前端在响应到达前无法确定配置是否已写盘，仍会被同步热重载阻塞。不新增“保存”和“应用”两个独立接口，因为现有队列已经提供所需生命周期，拆分接口会扩大调用方和中间状态。

## 后端设计

### 请求流程

`PUT /api/config` 保留当前事务前半段：

1. 加载并合并部分更新。
2. 执行字段、模型和姿态门禁校验。
3. 在 `_CONFIG_SAVE_LOCK` 内再次检查初始化状态。
4. 创建 `config.toml` 快照。
5. 写入新配置和待写凭据。
6. 递增 `config_apply_revision`，构造 `_QueuedConfigApply`。
7. 无条件调用 `_enqueue_config_apply(item)`。
8. 返回 HTTP 202、`apply_state="queued"` 和 `apply_revision`。

响应消息明确区分两个阶段：配置已经持久化，但运行时尚在后台应用。

### 后台应用

继续复用 `_run_config_apply_queue()`：

- 只应用当前最新的待处理修订；新的连续保存覆盖尚未开始的中间修订。
- 应用前设置代理等进程级配置。
- 通过 `_apply_runtime_config_revision()` 执行安全热重载。
- 成功后更新 `config_last_good`、`config_applied_revision` 和 apply status，并发布 `config_reloaded`。
- 失败时恢复 `config_last_good` 到配置文件，设置 failed 状态并发布 `config_reload_failed`。

删除 PUT 路由中的同步 fast path 与重复回滚分支，避免同步和异步两套实现继续漂移。初始化等依赖运行时稳定状态的入口继续使用 `_config_apply_busy()` 拒绝请求，直到后台配置应用完成。

### API 合约

成功写盘统一返回：

```json
{
  "ok": true,
  "message": "配置已保存到 …，正在后台应用。",
  "reloaded": false,
  "rollback_applied": false,
  "restart_required": false,
  "apply_state": "queued",
  "apply_revision": 12,
  "config": {}
}
```

HTTP 状态为 202。`reloaded=false` 表示响应时尚未完成热重载，不代表热重载被跳过。

## 前端设计

### 状态模型

设置保存栏增加独立的展示状态，优先级如下：

1. `dirty`：存在新的本地修改。
2. `saving`：当前 PUT 尚未确认写盘。
3. `applying`：后端已经写盘，正在应用某个修订。
4. `applied` / `failed` / `idle`：最近一次后台应用的终态。

保存栏文案：

| 状态 | 文案 | 按钮表现 |
| --- | --- | --- |
| dirty | `已修改 N 项，未保存` | “保存配置”可用 |
| saving | `正在保存配置…` | “保存中…”禁用，保存栏 `aria-busy=true` |
| applying | `配置已保存，正在后台应用…` | 结束请求忙态；没有新修改时按钮按正常规则禁用 |
| applied | `配置已应用` | 正常 |
| failed | `配置应用失败，已恢复上一次生效配置` | 正常，并显示错误 Toast/状态 |
| idle | `没有未保存的修改` | 正常 |

`renderSettingsDirty()` 扩展为统一渲染保存栏状态，不能在 `saving` 时继续显示“未保存”。“解除保存按钮”指结束请求忙态并恢复“保存配置”文案；当修改已经成功保存且 dirty count 为 0 时，按钮仍按原规则禁用，避免提交空更新。

### 保存响应

提交开始时设置 `saving`，同时禁用保存和放弃修改。收到 HTTP 202 后：

- 使用响应中的配置清空对应 dirty 状态。
- 记录 `apply_revision` 为当前等待应用的修订。
- 结束 `settingsSaveInFlight`。
- 保存栏切换为 `applying`，显示精确文案“配置已保存，正在后台应用…”。
- 不在此时主动执行会把状态改成“配置已从后端加载”的完整再水合；等待运行时事件触发同步。
- 更新检查等与配置应用无关的后台刷新可以继续异步执行。

### 运行时事件

`config_reloaded` 与 `config_reload_failed` 都携带 `revision`。前端只处理不旧于当前等待修订的事件：

- `config_reloaded`：清除等待修订；若没有新的 dirty 修改，保存栏显示 `配置已应用`，随后调度后端再水合。
- `config_reload_failed`：清除等待修订；显示失败状态、配置状态文本和 Toast，并调度读取回滚后的配置。
- 如果用户正在编辑表单，沿用现有保护，不用后端再水合覆盖输入；保存栏优先显示新的 dirty 状态。

旧修订事件不能清除更新修订的 applying 状态。新的本地修改不能被任何旧事件改回 applied 文案。

### 事件竞态与重连恢复

后台任务由 `asyncio.create_task` 启动，快速热重载可能在浏览器收到 202 并记录 `apply_revision` 之前就发布 `config_reloaded`。因此前端不能只依赖事件：

- 增加 `configApplyStatus: "/config/apply-status"` 端点映射。
- 收到 202 并记录修订后，立即读取一次 apply status；若已经 applied/failed，直接进入终态。
- 若状态仍为 queued/applying，则等待运行时事件。
- 实时事件连接首次建立或重连时再读取一次 apply status，补偿断线期间丢失的终态事件。
- 不进行固定周期轮询；长时间热重载仍由事件完成通知，避免在最长 25 分钟安全排空窗口内持续请求。

## 错误处理

- 校验失败、初始化中、快照失败或写盘失败仍在 PUT 请求内返回错误；前端保留 dirty 状态并显示失败详情。
- 写盘成功后的热重载失败属于异步失败，由后台队列完成回滚并通过事件通知。
- 页面通过 `/api/config/apply-status` 在 202 响应后和实时连接建立/重连时恢复 applying/applied/failed 状态，不以永久等待事件为唯一恢复方式。
- 连续保存沿用 latest-wins 语义；每次 202 都用更大的 `apply_revision` 替换前端等待修订。

## 测试设计

### 后端

1. 新增空闲通道回归测试：用事件阻塞 `RuntimeContext.rebuild_from_config`，断言 PUT 在阻塞解除前返回 202，且配置文件已经包含新值。
2. 解除阻塞后轮询 apply status，断言状态最终为 applied、修订号一致且运行时使用新值。
3. 保留并扩展连续保存 latest-wins 测试。
4. 保留后台应用失败恢复最后一次成功配置的事务测试。
5. 验证初始化等需要稳定运行时的入口在 applying 时仍返回 `config_applying`。
6. 验证浏览器扩展现有配置客户端接受 202，不依赖固定的 200 状态码。

### 前端

1. 测试保存开始后保存栏显示 `正在保存配置…`，不再显示 `已修改 N 项，未保存`。
2. 测试 202 响应后显示精确文案 `配置已保存，正在后台应用…`，按钮恢复原文案且 busy 属性解除。
3. 测试较旧的 `config_reloaded` 事件不会清除较新的等待修订。
4. 测试匹配修订成功后显示 `配置已应用`。
5. 测试后台失败显示回滚提示；存在新 dirty 修改时，不覆盖 dirty 状态。
6. 测试 202 后立即读取 apply status，并能补偿“成功事件早于 202 响应到达”的竞态。
7. 测试实时连接建立或重连时刷新 apply status。

### 浏览器验收

在本地 `/web` 修改一个可恢复的占比并保存：

1. 观察 saving 文案立即出现。
2. 确认写盘响应后快速进入 applying 文案，按钮不持续停留在“保存中…”。
3. 确认最终收到 applied 状态。
4. 读取 `/api/config` 验证值；再恢复原值并重复验证。
