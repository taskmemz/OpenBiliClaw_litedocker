# 桌面 Web 保存列表徽标初始化设计

**日期：** 2026-08-06

**范围：** 桌面 Web `/web` 侧栏的“稍后再看”和“收藏”数量徽标

**不在范围：** 保存列表接口、数据库结构、移动 Web、小红书候选或来源占比

## 问题

桌面 Web 刷新后，后端的 `/api/saved/watch_later` 已返回真实总数，但侧栏“稍后
再看”徽标仍保持隐藏。只有用户进入“稍后再看”页面后，`refreshWatchLater()`
才会读取列表并调用 `updateSavedBadge()`，因此数量会在点击后才出现。

“收藏”使用相同的加载结构，也没有加入首次 `hydrateFromBackend()` 流程。当前收藏
为空时看不出异常，但存在同样的初始化遗漏。

## 目标

1. 页面刷新后，无需点击侧栏 Tab，“稍后再看”和“收藏”徽标都展示后端返回的
   最新总数。
2. 数量为零时继续隐藏徽标，保持现有视觉语义。
3. 保存列表读取失败时静默降级，不阻塞推荐列表、运行状态或其他首屏内容。
4. 保留现有列表页面的刷新、任务恢复和保存按钮状态同步行为。

## 方案

采用前端启动水合方案，不增加后端计数接口。

- 复用现有 `syncWatchLaterButtons()` 和 `syncFavoriteButtons()`。两个函数已经读取保存
  列表、同步可见卡片按钮状态并更新对应徽标，只是当前没有被启动流程调用。
- 让两个同步函数返回其请求 Promise，使 `hydrateFromBackend()` 能把它们纳入现有
  `Promise.allSettled()` 后台水合任务。
- 页面首次水合时并行启动两个同步函数。它们继续使用已有的失败吞吐逻辑，单个保存
  列表接口失败不会让整个水合流程失败，也不会显示错误占位。
- 列表接口响应中的 `total` 是徽标唯一计数来源；前端不使用首批 `items.length`
  推算总数，因此保存条目超过单页上限时仍展示真实总数。
- 每个列表维护启动徽标同步代次。用户进入保存列表触发完整刷新时推进对应代次，
  更早发出、但更晚返回的启动响应不再覆盖完整刷新得到的新徽标和按钮状态。

## 数据流

1. 桌面 Web 完成 `/api/ping` 健康检查。
2. `hydrateFromBackend()` 与其他次级资源并行请求
   `/api/saved/watch_later?limit=200&offset=0` 和
   `/api/saved/favorite?limit=200&offset=0`。
3. 每个请求成功后，现有同步函数更新可见卡片按钮的 `aria-pressed` 状态，并将响应
   `total` 交给 `updateSavedBadge()`。
4. `total > 0` 时显示数字；`total = 0` 时隐藏徽标。
5. 请求失败时保留徽标的初始隐藏状态，其余首页资源继续加载。

## 测试

先写失败测试，再实现：

1. 使用真实 Chromium 打开桌面 Web，测试服务令“稍后再看”返回 `total = 3`、
   “收藏”返回 `total = 2`。
2. 不点击任何侧栏 Tab，等待首次水合完成后直接断言两个徽标分别显示 `3` 和 `2`。
3. 同一测试确认两个保存列表接口都在首次加载阶段收到请求，避免仅靠静态源码断言。
4. 延迟启动阶段的“稍后再看”响应，让用户点击后的完整刷新先返回 `total = 4`，
   再释放旧响应 `total = 3`；断言徽标最终仍为 `4`。
5. 运行相关桌面 Web 单元测试和真实浏览器集成测试。
6. 在本地实际后端已有 3 条“稍后再看”的环境刷新 `/web`，确认点击前徽标即显示
   `3`，并确认进入列表后数量没有变化。

## 验收标准

- 刷新 `/web` 后，“稍后再看”和“收藏”在数量大于零时无需点击即可显示徽标。
- 点击任一 Tab 前后，徽标数量保持一致。
- 任一保存列表接口失败不影响推荐首页正常渲染。
- 不修改保存列表 API、数据库、移动端或内容来源逻辑。
- 针对性自动化测试和本地浏览器验收通过。
